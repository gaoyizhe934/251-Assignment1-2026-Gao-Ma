每日开工清单：
每次开始新一天的工作，先逐项列出当前问题/任务及其解决方式。
创建分支前先明确工作类型：新增功能、测试、重构、文档等；分支命名须与该类型匹配，不再自行模糊命名。
若任务类型不清楚，先基于任务卡和变更范围判定，再开始操作。
确认今日工作时间范围
临近截止时间时停止扩展任务，优先完成验证、保存现场和交接。
到达截止时间后，不擅自继续工作；未完成内容如实列出。

检查本地 Git 状态
提交git，分支，pr正文，comment的时候一定要保证文本语言是中文
pr创建要求保持固定格式：例如：DX（X为阶段数或天数，不能只写X）A（A/B/C...轨道名）：（所实现的功能）
确认仓库、当前分支和远程地址。
检查未提交、未暂存及未跟踪文件。
发现本地改动时，先报告，避免同步操作覆盖或干扰现有内容。

同步 GitHub 代码
获取远程最新状态并比较本地差异。
在安全的情况下同步当前分支，默认避免产生不必要的合并提交。
如有冲突、分支分叉、认证失败或网络问题，立即报告，不擅自覆盖文件或改写历史。
新的一天需要重新写新的PR，不得修改其他人的PR作为自己的。
在被review打回之后修改之后需要在后面写新的修改报告发布comment，不得更改原始的PR正文
记录技术债的时候先记录到技术债文档，在同步到github issues里面，命名规则和其他的TD一样
需要变到分支的时候不要rebase，一律都用pull

确认今日任务范围
复述今日目标、交付物和验收标准。
区分：今日必须完成；
有余力再完成；
明确不在今日范围内。
不自行扩大需求。

列出今日工作清单
将任务拆分成可检查的具体工作项。
标明执行顺序、依赖关系和验证方式。
给出初始进度，例如：总进度：0/6（0%）。

持续显示工作进度
每完成一项工作，立即更新：当前完成项；
总进度；
已运行的检查及结果；
下一项工作；
剩余时间或时间风险。
示例：总进度：3/6（50%），下一项：运行功能测试。

规范管理文件
不移动或覆盖用户原始资料。
中间文件统一放入 辅助生成文件 的对应子目录。
最终交付物默认放入 可直接查看。
不在工作区根目录散落临时脚本、缓存和渲染文件。
未经授权不删除原始资料、正式成果或用途不明的文件。

修改后进行充分验证
根据改动运行适当的测试、构建、检查或文档渲染。
不隐瞒失败、警告、未覆盖场景和已知风险。
不为了赶时间虚报完成；时间不足时保存进度并清楚交接。
在每一次修改过后逐文件列出修改原因

Commit 前强制人工审核
完成修改和验证后停止操作，把控制权交还给你。
提供：修改文件清单；
Diff 摘要；
测试与检查结果；
已知风险、阻塞和未完成事项；
建议的提交信息。

默认不执行 git add，方便你审核工作区 Diff。
在你看过审核材料并再次明确说“commit”之前，绝不私自提交。

Git 操作分别授权
commit、push、创建 PR、合并 PR分别需要明确指令。
“继续”“完成全部工作”等表述不视为 commit 授权。
如果审核后又发生实质修改，重新提供审核材料并再次等待授权。
不擅自执行会覆盖文件或改写历史的操作。

当日收尾
汇总已完成、未完成和被阻塞的事项。
说明当前 Git 状态及文件位置。
给出下次继续工作的明确起点。

提交分支要求：
分支禁止codex/命名，需要严格按照命名规则，检查到了就立马按要求更改
分支命名单纯 ASCII 分支名    
pr命名时前面要加第几天的第几轨内容，格式例：D1B test: 建立V0.3规则引擎测试骨架
主分支不能直推，需要创建一个分支，以你当前的目的类型/具体实现命名
feat: 新功能 (feature也行，两者都可以)
fix: 修补 bug
docs: 文档变更
style: 代码格式（不影响代码运行的变动，如空格、分号）
refactor: 重构（既不是新增功能，也不是修改 bug）
perf: 性能优化
test: 增加测试
chore: 构建过程或辅助工具的变动
例如
分支名这么写：feature/CardManager
commit这么写：fix(CardManager)：修复了出牌卡住的bug

要原子化提交，修一个小bug就可以提交一次，不要攒个大的，不然之后除了问题不好回退
提交PR前，应该先在本地 pull 一下 main 分支，解决冲突后再推送
